# RefBraid — чего не хватает

Список задач составлен 2026-11-17 по исходникам версии 0.3.4 (`app/src`) и обновлён 2026-11-20 по коммитам до `dec1d3d` и несохранённым в коммитах доработкам этого дня. Он показывает, каких возможностей привычного Git-клиента в программе пока нет или что сделано частично.

У сделанных задач под заголовком стоит пометка «Реализовано после 0.3.4» с тем, что вошло и что осталось; описание под ней — исходная постановка. Что появилось помимо списка, перечислено в разделе «Сделано сверх списка» в конце.

Каждая задача описана одинаково:

- **Зачем** — какую проблему пользователя она решает.
- **Сейчас** — что уже есть в коде.
- **Сделать** — что должно появиться.
- **Где** — модули, которые придётся менять.
- **Готово, когда** — как понять, что задача закрыта.

Общие правила для всех задач (подробно в `CLAUDE.md`):

- git вызывается только через `git::run` / `git::command`, libgit2 не используется;
- изменяющие операции идут через `Job` и `App::run_job`, чтение — синхронно или по своему каналу;
- модальные окна строятся через `form::show`, цвета и значки берутся из `theme.rs`;
- для труднодоступного экрана добавляется переключатель `REFBRAID_VIEW`;
- текст интерфейса английский.

Размер: **S** — до дня, **M** — несколько дней, **L** — неделя и больше.

## 1. Высокий приоритет

Без этих возможностей клиент не заменяет командную строку в ежедневной работе.

### 1.1. Interactive rebase (L) — сделано

> Реализовано после 0.3.4: окно **Interactive Rebase** (`rebase.rs`, `rebase_view.rs`) и пункты меню журнала `Interactively Rebase from Here…`, `Squash Commits…`, `Squash into Parent…`, `Drop Commit…`, `Edit Commit Message…` для любого коммита. Кнопка **Suggest with AI** в окне просит AI-агента из настроек предложить план (что склеить, переименовать, удалить, переставить); его можно отменить кнопкой Undo и поправить вручную. Не сделано: перетаскивание строк мышью (есть кнопки и `Alt+↑/↓`) и диапазоны с merge-коммитами — для них окно не открывается.

- **Зачем.** Перед отправкой ветки историю приводят в порядок: склеивают правки, переименовывают и выбрасывают коммиты. Это самая частая причина уйти в терминал.
- **Сейчас.** Есть `Rebase '<ветка>' onto …`, `Edit Commit Message…` (только для последнего коммита, через `commit --amend`) и продолжение/отмена начатого rebase.
- **Сделать.**
  - Пункт журнала `Interactively Rebase from Here…` открывает окно со списком коммитов от выбранного до `HEAD`.
  - Для каждого коммита выбирается действие: pick, reword, squash, fixup, drop; строки можно переставлять.
  - Быстрые пункты для выделенных коммитов: `Squash Commits…`, `Fixup`, `Drop Commit`, `Edit Commit Message…` для любого коммита, а не только последнего.
  - Запуск через `git rebase -i` с `GIT_SEQUENCE_EDITOR`, который подставляет готовый список (сам бинарник в роли редактора, как сделано для askpass).
  - При конфликте работает существующая панель разрешения конфликтов и кнопки Continue / Skip / Abort.
- **Где.** `log_view.rs` (меню), новый `rebase_view.rs`, `app.rs` (`Dialog`, `Job` с `env:`), `main.rs` (режим редактора), `git.rs`.
- **Готово, когда.** Три коммита можно склеить в один, поменять местами и переименовать без терминала; при конфликте rebase доводится до конца из программы; отправленные коммиты помечены предупреждением.

### 1.2. История файла (M) — сделано

> Реализовано после 0.3.4: пункт `Show History` в меню файла (Changes, файлы коммита, diff) открывает вкладку журнала `History: <файл>` с `git log --follow`; слева список коммитов и под ним детали выбранного коммита, справа diff файла в этом коммите (с колонкой Git Blame по желанию). В строке фильтров вкладки оставлены только текст, пользователь и дата, метки веток в строках списка убраны. После 0.3.5: `Show History for Selection` в меню diff открывает вкладку `History: <файл>:<строки>` с коммитами, менявшими выделенные строки (`git log -L`); кнопка с веткой в строке фильтров добавляет коммиты всех веток (`--all`); хеш показывается и в узком списке. Не сделано: в истории строк справа виден diff всего файла, а не только выбранных строк; для локальных изменений номера строк берутся из рабочего файла, а история читается от `HEAD`, поэтому при несохранённых правках выше выделения диапазон может сместиться.

- **Зачем.** «Кто и когда менял этот файл» — второй по частоте вопрос после просмотра журнала.
- **Сейчас.** В журнале есть фильтр по пути, но он не идёт через переименования и не вызывается из списка файлов.
- **Сделать.**
  - Пункт `Show History` в меню файла: в Changes, в файлах коммита, в diff.
  - Отдельная вкладка журнала по файлу с `git log --follow`; у каждой записи виден diff именно этого файла.
  - `Show History for Selection` для выделенных строк (`git log -L`).
- **Где.** `git.rs` (`LogQuery` с `follow`), `log_view.rs`, `commit_view.rs`, `details_view.rs`.
- **Готово, когда.** Для переименованного файла показана история до переименования, а щелчок по записи открывает его diff в этом коммите.

### 1.3. Blame / Annotate (M) — сделано

> После 0.3.5 во вкладке появилась подсветка синтаксиса (см. 1.6). Реализовано после 0.3.4: пункт `Annotate` в меню файла (Changes, файлы коммита, diff) открывает вкладку `Annotate: <файл>` (`blame.rs`, `blame_view.rs`): дата, автор и хеш у каждой группы строк, более новые коммиты окрашены сильнее, щелчок переходит к коммиту в журнале, есть `Annotate Previous Revision`. В просмотре различий пункт `Annotate with Git Blame` включает колонку с датой и автором у каждой строки новой версии — в режимах «Рядом», «Единым списком» и во вкладке истории файла. `git blame` выполняется в фоновом потоке. Не сделано: выделение текста во вкладке; открытая вкладка не обновляется при изменении файла.

- **Зачем.** Узнать, каким коммитом и кем написана конкретная строка.
- **Сейчас.** Нет ничего.
- **Сделать.**
  - Пункт `Annotate` в меню файла и в diff.
  - Слева от текста колонка: дата, автор, короткий хеш; строки одного коммита закрашены одним оттенком.
  - Щелчок по колонке выбирает коммит в журнале; `Annotate Previous Revision` идёт на шаг назад.
  - Данные из `git blame --porcelain`, загрузка в фоне.
- **Где.** `git.rs` (разбор porcelain), новый `blame_view.rs`, `split_view.rs`.
- **Готово, когда.** Файл в 5000 строк аннотируется без подвисания окна, переход к коммиту работает.

### 1.4. Clone и Init (M) — сделано

> Реализовано после 0.3.5 (`clone_view.rs`): `File → Clone…` и кнопка на экране приветствия открывают окно с адресом, папкой назначения, именем папки (подставляется из адреса), веткой, глубиной и галочкой подмодулей; клонирование идёт как обычная задача с ходом выполнения и отменой, затем репозиторий открывается. `File → New Repository…` выполняет `git init` в выбранной папке; если открыть папку без репозитория, программа предлагает создать его. Не проверено: клонирование по HTTPS и SSH с запросом пароля (проверен клон по `file://`).

- **Зачем.** Сейчас программой нельзя начать работу с нуля: репозиторий надо сначала получить в терминале.
- **Сейчас.** Только `Open Repository…` для существующей папки.
- **Сделать.**
  - `File → Clone…`: URL, папка назначения, необязательные ветка и глубина (`--depth`), галочка `--recurse-submodules`.
  - Ход выполнения клонирования и кнопка отмены (см. 3.4).
  - `File → New Repository…` (`git init`) и предложение создать репозиторий, если открыта папка без `.git`.
  - Оба пункта на экране приветствия.
- **Где.** `chrome.rs` (меню, welcome), `dialogs.rs`, `app.rs`. `Job` сейчас привязан к открытому репозиторию — для clone нужен запуск без него.
- **Готово, когда.** Репозиторий клонируется по HTTPS и SSH с запросом пароля через askpass и сразу открывается.

### 1.5. Reflog (M) — сделано

> Реализовано после 0.3.4: `Git → Reflog` открывает вкладку **Reflog** (`reflog.rs`, `reflog_view.rs`) с записями о перемещениях `HEAD`: время, коммит, действие. Коммиты, до которых не доходит ни одна ветка или тег, помечены `lost`; есть фильтр «Only lost commits». Справа — детали коммита и список его файлов. В меню записи: `New Branch…`, `Reset Current Branch to Here…`, `Checkout Revision`, `Show in Log`. Не сделано: показ недостижимых коммитов в графе журнала, просмотр diff файлов потерянного коммита, reflog отдельных веток (читается только `HEAD`).

- **Зачем.** Вернуть коммиты после неудачного reset, rebase или удаления ветки. Для клиента, где reset доступен в два щелчка, это страховка.
- **Сейчас.** Нет.
- **Сделать.**
  - Режим журнала или отдельная вкладка `Reflog` (`git reflog --format=…`) с действием и временем каждой записи.
  - Для записи: `Checkout`, `New Branch from Here…`, `Reset Current Branch to Here…`.
  - Недостижимые коммиты можно показать в графе.
- **Где.** `git.rs`, `log_view.rs` или новый `reflog_view.rs`.
- **Готово, когда.** После `Reset --hard` потерянный коммит находится и возвращается веткой.

### 1.6. Подсветка синтаксиса в diff (M) — сделано

> Реализовано после 0.3.5 (`syntax.rs`): собственный лёгкий разметчик без внешних библиотек. Раскрашиваются ключевые слова, типы, строки, числа, комментарии и вызовы функций в Rust, Python, JS/TS, C/C++, Java/Kotlin/C#, Go, Swift, PHP, Ruby, shell, SQL; ключи и значения в JSON, YAML, TOML; заголовки, код и ссылки в Markdown; теги и атрибуты в HTML/XML; CSS. Работает в обоих режимах diff, во вкладке истории файла и в Annotate; многострочные комментарии и строки отслеживаются отдельно для старой и новой версии. Разметка считается один раз при открытии diff; подсветка изменённых слов накладывается поверх. Выключатель — Settings → Window → Diff. Позже раскрашено и окно разрешения конфликтов: все три колонки, включая редактируемый результат; открытый выше комментарий или многострочная строка продолжаются через блоки. Не сделано: язык определяется только по имени файла; файлы больше 4 МБ и строки длиннее 4000 символов не раскрашиваются.

- **Зачем.** Код без подсветки читается заметно хуже, особенно в режиме Side-by-side.
- **Сейчас.** Подсвечиваются только изменённые слова (`wordiff.rs`).
- **Сделать.**
  - Раскраска по расширению файла; библиотека `syntect` или лёгкий собственный разметчик для основных языков.
  - Цвета синтаксиса в `theme.rs`; подсветка изменённых слов накладывается поверх.
  - Разметка считается один раз на файл и кешируется, большие файлы — лениво по видимым строкам.
  - Выключатель в Settings.
- **Где.** `split_view.rs`, `commit_view.rs` (Unified), `merge_view.rs`, `theme.rs`, `Cargo.toml`.
- **Готово, когда.** Rust, Python, JS/TS, JSON, YAML, Markdown раскрашены, прокрутка файла в 10 000 строк остаётся плавной.

### 1.7. Поиск по тексту в diff (S) — сделано

> Реализовано после 0.3.5 (`find.rs`): `Ctrl+F` во вкладке diff и в diff истории файла (или пункт `Find…` в меню) открывает строку поиска: подсветка совпадений, счётчик «N из M», `F3` / `Shift+F3` / `Enter`, учёт регистра и регулярные выражения, `Esc` закрывает. Совпадение среди свёрнутых строк разворачивает их. Работает в режимах «Рядом» и «Единым списком». Позже добавлен поиск в окне разрешения конфликтов: `Ctrl+F` ищет в трёх колонках, строки без конфликта считаются один раз (в результате), найденное место прокручивается в вид по вертикали и по горизонтали, `Esc` закрывает строку поиска, а не окно. Не сделано: замена найденного.

- **Зачем.** В длинном diff нужное место ищут по слову.
- **Сейчас.** `Ctrl+F` переносит в поиск по журналу.
- **Сделать.** Когда фокус в diff, `Ctrl+F` открывает строку поиска над ним: подсветка совпадений, счётчик, `F3` / `Shift+F3`, учёт регистра и регулярные выражения (виджет `search_box` уже есть).
- **Где.** `chrome.rs` (разбор сочетания), `split_view.rs`, `commit_view.rs`.
- **Готово, когда.** Поиск работает в обоих режимах diff и в окне разрешения конфликтов.

### 1.8. Журнал больших репозиториев (L) — сделано

> Реализовано после 0.3.5: журнал читается в отдельном потоке; если чтение длится дольше четверти секунды, окно продолжает работать со старым списком и показывает «Loading the log…», а новый список подставляется по готовности. При прокрутке к концу подгружается следующая порция (ещё столько же коммитов). Когда задан текст поиска, под фильтрами появляется строка с числом найденного и ссылками «Search the whole history» (`git log --grep` по сообщениям всех коммитов) и «Search in the changes» (`git log -S`). Сортировка «по веткам» теперь выполняется самим git (`--topo-order`) в пределах лимита. Проверено на искусственном репозитории в 300 000 коммитов: первая порция читается около секунды в фоне, старый коммит находится по тексту сообщения. Позже из потока интерфейса вынесены `git status` (после собственной операции программа ждёт его, при автообновлении, `F5` и открытии репозитория — не дольше четверти секунды) и поиск веток, содержащих коммит (`branch --contains`: на 300 000 коммитов 2,8 с на каждый щелчок; теперь детали показываются сразу, ветки дописываются по готовности, одновременно идёт не больше двух поисков). Достраивание графа и `--skip` решено не делать — замер на 300 000 коммитов (release): `git log --date-order` занимает 1,3–2,1 с почти независимо от `-n` и `--skip` (время уходит на обход истории), разбор и раскладка графа — 0,06 с на 100 000 коммитов и 0,22 с на 300 000, и всё это уже в фоновом потоке. Заметно ускорить догрузку может только файл commit-graph в самом репозитории (`git commit-graph write --reachable`). Не сделано: на ядре Linux не проверялось.

- **Зачем.** На репозиториях в сотни тысяч коммитов окно подвисает, а старая история недоступна.
- **Сейчас.** `git::load_log` читает `git log -n <limit>` (по умолчанию 5000) синхронно в потоке интерфейса. Текстовый фильтр и фильтр по автору применяются только к уже загруженным коммитам.
- **Сделать.**
  - Загрузка журнала в рабочем потоке по каналу, интерфейс не блокируется; в строке состояния виден ход загрузки.
  - Догрузка следующей порции при прокрутке к концу (`--skip` или продолжение от последних хешей).
  - Если фильтр задан, а загружена не вся история, искать через git: `--grep`, `--author`, `-S` / `-G` (поиск по содержимому изменений).
  - Раскладка графа (`graph.rs`) должна уметь достраиваться, а не считаться заново.
- **Где.** `git.rs`, `app.rs` (`reload_log`, `LogState`), `graph.rs`, `log_view.rs`.
- **Готово, когда.** Репозиторий ядра Linux открывается без подвисания, старый коммит находится по тексту сообщения.

### 1.9. Параметры merge (S) — сделано

> Реализовано после 0.3.5: пункт `Merge with Options…` в меню ветки, удалённой ветки и тега открывает окно с выбором «по умолчанию / `--no-ff` / `--ff-only` / `--squash`», галочкой `--no-commit` и сообщением; выбор запоминается. После squash и `--no-commit` открывается панель Commit с подготовленным сообщением. Быстрый пункт `Merge '<ветка>' into …` остался.

- **Зачем.** В командах приняты разные правила слияния: всегда merge-коммит, только fast-forward или squash.
- **Сейчас.** `Merge '<ветка>' into '<текущая>'` всегда выполняет `git merge --no-edit`.
- **Сделать.** Окно `Merge…` с выбором `--no-ff` / `--ff-only` / `--squash`, галочкой `--no-commit` и полем сообщения. Последний выбор запоминается в настройках. Пункт контекстного меню остаётся быстрым путём с настройками по умолчанию.
- **Где.** `branch_menu.rs`, `branches_view.rs`, `dialogs.rs`, `settings.rs`.
- **Готово, когда.** Все три вида слияния выполняются из окна, после squash открывается панель Commit с подготовленным сообщением.

## 2. Средний приоритет

Нужны не каждый день, но их отсутствие заметно.

### 2.1. Stash: просмотр и частичное применение (M) — сделано

> Реализовано после 0.4.0: у каждого stash кнопка `Show Files` раскрывает список его файлов (изменённые, удалённые и неотслеживаемые, убранные вместе с ними); щелчок открывает diff файла, пункт `Take This File` кладёт один файл в рабочую папку (`git restore --source=<stash> --worktree`), stash при этом остаётся; если у файла есть свои изменения, сначала спрашивается подтверждение. В окне `Stash Changes` добавлены `--keep-index` и «только выбранные файлы» (те, что выделены в Changes). Кнопка `Branch…` создаёт ветку из stash (`git stash branch`). Не сделано: файл, который stash удаляет, взять нельзя; применение отдельных изменений внутри файла.

- **Сейчас.** Список stash с Apply / Pop / Drop, создание с сообщением и `--include-untracked`.
- **Сделать.**
  - Просмотр файлов и diff выбранного stash до применения (`git stash show -p`).
  - Применение отдельных файлов из stash.
  - Stash только выбранных файлов (`git stash push -- <пути>`) и `--keep-index`.
  - `New Branch from Stash…` (`git stash branch`).
- **Где.** `git.rs` (`stashes`), `commit_view.rs`, `dialogs.rs`.
- **Готово, когда.** Содержимое stash видно до применения, из него можно взять один файл.

### 2.2. Worktrees: управление (S) — сделано

Не сделано: новый ключ создаётся без парольной фразы; сохранённый неверный пароль из программы не удаляется; само подключение к новому серверу по SSH вживую не проверялось — проверены разбор вопроса и создание ключа.

- **Сейчас.** Запрос пароля через собственный askpass (`askpass.rs`).
- **Сделать.** Разбор типичных ошибок авторизации с подсказкой, что делать; страница настроек с выбранным credential helper и ключами SSH (список, создание, копирование публичного ключа); вопрос о незнакомом ключе хоста SSH показывается окном, а не зависает.

### 3.7. Пробелы, окончания строк и кодировки (S) — сделано

> Реализовано после 0.4.2: в панели diff пункт `White space` — показывать все изменения, игнорировать изменение количества пробелов (`-b`) или все пробелы (`-w`); выбор запоминается и действует на все diff (файлы коммита, локальные изменения, сравнение ревизий). Пока пробелы игнорируются, частичный коммит и откат отдельных изменений в diff отключены: они считаются по точному diff. Изменённые файлы, у которых отличаются только окончания строк (CRLF / LF), помечены в списке Changes словами «только окончания строк». Settings → Window → Diff: кодировка для файлов не в UTF-8 (Windows-1251, Windows-1252, CP866, KOI8-R) — так читаются только строки, не являющиеся верным UTF-8 (`encoding.rs`). Не сделано: кодировка одна на всю программу, а не на файл; UTF-16 не распознаётся; частичный коммит файла не в UTF-8 по-прежнему ненадёжен.

- **Сейчас.** Diff всегда учитывает пробелы; вывод git читается как UTF-8 с заменой неверных байтов.
- **Сделать.** Переключатель в diff: не игнорировать / игнорировать изменения пробелов (`-b`) / все пробелы (`-w`); пометка файлов, где изменились только окончания строк; выбор кодировки для файла не в UTF-8 (например, Windows-1251) вместо «кракозябр».
- **Где.** `git.rs` (`parse_diff` и вызовы `diff`), `split_view.rs`, `commit_view.rs`.
- **Готово, когда.** Файл с переформатированными отступами показывает только смысловые изменения.
